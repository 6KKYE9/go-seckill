# go-seckill

一个高并发秒杀系统的骨架，纯标准库。核心就解决一个问题：**100 件商品，一万个人同时抢，不能卖出 101 单（超卖），也不能让一个人买两次**。

## 跑起来

```powershell
go run . -stock 100 -queue 1000
```

`-stock` 是库存，`-queue` 是异步队列长度。

## 接口

```powershell
# 同步秒杀：直接告诉你能不能买
curl "http://127.0.0.1:9400/seckill?user=alice"

# 异步秒杀：先入队，返回 queued，成绩稍后查
curl "http://127.0.0.1:9400/seckill/async?user=bob"
curl "http://127.0.0.1:9400/result?user=bob"

# 查库存和活动统计
curl "http://127.0.0.1:9400/stats"
```

## 怎么做到不超卖

两层防护：

**第一层：原子计数器快速拦截**
每个请求进来先 `atomic.AddInt64(&claimed, 1)`。如果占位数已经超过库存，立刻把占位还回去、返回售罄，**根本不进锁**。这一层把绝大多数超额请求挡在门外，锁就不会被海量请求挤爆。

**第二层：加锁精确扣减**
真正能买到的人很少，进锁后做三件事：去重（同一 user 只能一次）、再校验一次库存（因为原子层可能多放几个进来）、扣库存、记成功。锁内逻辑串行，库存绝不会算错。

**异步削峰**
`/seckill/async` 把请求丢进一个带缓冲的 channel 队列，后台一个 worker 慢慢处理。前端秒级拿到"已受理"，不用卡在锁上等，成绩以 `/result` 查为准。这是秒杀系统常见的"排队"思路，把瞬时尖峰削平。

## 没做的事

- 没接数据库，库存在内存，重启就没
- 没做 Redis 分布式锁，多机部署时这套锁只保护单进程
- 没做防刷（同一个 user 疯狂请求没限流）、没做验证码/答题拦机器人
- 订单没落库，成功只是记个数

## 测试

```powershell
go test ./...
```

最关键的是 `TestNoOversell`：1000 个 goroutine 抢 100 库存，验证成功数正好等于 100、库存归零、无超卖、无重复。并发下跑很多次都稳。
